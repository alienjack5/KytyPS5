Of these, the ones a continuation can skip with a cover: `findbuffers` for exact-range slots (the lookup result is the recorded id; cover: the `verify` lookup compare), the vertex/index binds when identical to the previous draw's (cover: the engine suite's pixel comparison), the record fill churn. The rest is per-draw data movement, the draw command, or the late image check. Written into design.md D3.
- [x] 4.2 Done and measured (`_console-20261018-171641.txt`, same area): neutral within run-to-run noise (`cont` commit 4.72 vs 4.65 µs with D1 alone). Only the in-place record fill is kept. ## Workflow follow-up

- Commit the change (code, tests, docs, preset) and add its `docs/CHANGE-CATALOG.md` entry with the commit hash; then archive the change.
- `KYTY_DRAW_RUN=exit` stops ASTRO's PLAYROOM within ~25 s of heavy gameplay on `part=acquisition` / `CPU dirty` (pre-existing, see 5.2): either the acquisition verify should tolerate a CPU-dirty flag that arrives between its two snapshots (it is set from the write-tracking path, asynchronously), or the continuation path should re-check CPU-dirty textures after acquisition. Investigate before relying on `KYTY_DRAW_RUN=exit` as a gate.
- Unit test with an indexed draw and a vertex buffer that repeat across a run, so the vertex-range and index entries of the record are exercised by the suite and not only in-game (`CheckDrawRunBindings` covers the pixel stage's V# today).
- Open the follow-up proposals the design excludes: a run-level commit with per-draw data addressed through buffer device addresses (the step that could take a continuation under 2 µs), rendering-instance boundary cost (216 per frame at ~30 µs), spin-versus-park policy of the waiting threads.
